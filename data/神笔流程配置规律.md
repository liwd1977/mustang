# 神笔流程配置规律

> 本文档汇总野马智能交付工作台写入神笔平台时的配置规律，随开发持续维护。  
> 最后更新：2026-08-14

---

## 1. 平台层级与 ID 绑定

```
应用 appId ──→ wfSimpleProc.appId
                │
表单 formId  ←── wfSimpleProc.fromId
  │ tableName = procKey = cslcX_XXXXXX（平台自动生成）
  │
流程 procId  ←── wfSimpleProc.id
```

| 字段 | 说明 |
|------|------|
| `appId` | 每个 workflow 独立应用；首次写入调用 `tBaidaApp/saveOrUpdate` 创建，registry 记录后更新复用 |
| `tenantId` | 租户 ID，写入 `wfSimpleProc` |
| `formId` | 新建时为 null，首次 model-save 后平台分配 |
| `procId` | 同上 |
| `procKey` / `tableName` | 必须相同，格式 `cslcX_XXXXXX` |
| `fromId` | 必须等于 `formId` |

**命名规则（应用名 = 流程名）：**

- 来源：办事指南流程标题
- 去掉「表」及后缀状态，如「（已核对）」「（已核准）」
- 同步写入：`应用.mc` = `wfSimpleProc.procName` = `formModel.tableComment`

| 指南标题 | 应用名 / 流程名 |
|----------|----------------|
| 野马集团二线招聘需求表（已核对） | 野马集团二线招聘需求 |
| 外贸集团样车合同备案表（已核准） | 外贸集团样车合同备案 |

应用命名格式（新建）：`野马_{板块}_{流程简称}`；大类暂用「服务」。

## 2. model-save 提交规律

### 2.1 单次 save，单一 JSON

神笔设计器从「基础配置 / 表单 / 流程」三个 Tab 导出时，**内容完全相同**（已用同批次样例验证）。因此：

- **不再三步 save**，改为 **一次 model-save**
- 运行时 **不读取** `data/流程写入/*.txt`；样例 JSON 仅作人工对照参考
- 代码在 `core/workflow/shenbi_builder.py` 内 **程序化组装** 完整 model

### 2.2 新建 vs 更新（本地 registry）

每个工作流在本地维护一份 registry，用于记录平台已分配 ID，避免重复新建：

| 路径 | `output/workflows/shenbi/{slug}_registry.json` |
|------|------------------------------------------------|
| 索引键 | `workflow_name`（办事指南 catalog 键，如「外贸集团样车合同备案表」） |
| `{slug}` | `normalize_workflow_name(workflow_name)`，与 payload 文件名一致 |

**registry 字段：**

| 字段 | 说明 |
|------|------|
| `workflow_name` | catalog 键 |
| `app_id` | 神笔应用 ID |
| `app_mc` | 应用名称（与 `mc` / `procName` 一致） |
| `form_id` | 表单 ID |
| `proc_id` | 流程 ID |
| `proc_key` | 平台分配的 procKey（与 tableName 相同） |
| `table_name` | 数据表名 |
| `updated_at` | 最近一次写入时间 |

**写入策略：**

1. 生成 JSON 后，若 registry **存在** → 注入 `appId` / `formId` / `procId` / `procKey`，走 **更新**
2. registry **不存在** → 剥离 ID 与 procKey，走 **新建**（procKey 由平台分配）
3. model-save 成功后，将返回的 ID **写回 registry**
4. **相同 workflow_name** 再次一键写入 → 始终更新同一条流程，不新建

**写入顺序（无 registry 时）：**

1. `POST /fighter-baida/api/baida/tBaidaApp/saveOrUpdate` 创建应用  
   - `mc` = 流程显示名（如「野马集团二线招聘需求」）  
   - `yyjj` = 简介；`yydl` = `3`（服务）；`sfqy` = `1`  
2. `POST /fighter-baida/api/flow-simple/proc/model-save` 在同一 `appId` 下创建表单 + 流程  
3. 成功后写入 `{slug}_registry.json`（含 `app_id` / `app_mc` / `form_id` / `proc_id`）

**新建时 tableName / procKey：** 无 registry 时客户端生成 `cslc_{6位hex}`；`formId` / `procId` 由平台在 model-save 后分配。

代码入口：`core/workflow/shenbi_client.py` → `load_workflow_registry` / `save_workflow_registry` / `apply_registry_to_payloads`

### 2.3 请求体结构

**外层（API）：**

```json
{ "wfSimpleDefaultModel": "<Base64(内层 JSON)>" }
```

**内层（完整模型）：**

| 字段 | 说明 |
|------|------|
| `id` | 模型记录 ID，新建为 null |
| `formModel` | 表单字段、分组、按钮 |
| `formModelJson` | `formModel` 的 JSON 字符串（**写入前必须同步**，导出样例可能为 null） |
| `wfSimpleProc` | 流程基础属性 |
| `wfSimpleTaskInfo` | 环节树 |

### 2.4 复杂流程模板（参考）

复杂流程（并行/分支）样例见 **`data/流程写入/复杂流程配置JSON文件.txt`**（来源：招聘需求样例 `11.txt`）。  
**代码实现**：`core/workflow/complex_flow_builder.py` → `build_recruitment_task_tree()`（`flow_kind=complex_recruitment`）。

## 3. 表单双分组

| 分组 | 标签 | 内容 |
|------|------|------|
| `group[0]` | **表单信息** | 系统字段 + 业务字段 + 发起人 |
| `group[1]` | **审批意见** | 各 USERTASK 的审批意见 textarea |

线性与复杂流程 **均须** 包含「审批意见」分组（勿用「分组」「审批信息」）。

### 3.1 表单信息字段顺序

```
[系统隐藏字段：id、processInstanceId、taskId …]
→ 部门 (orgId)
→ 流程编号 (processCode)
→ 发起人 (fqr)
→ [OA 业务字段，按一键写入补充顺序追加]
```

- 部门、流程编号：创建流程时平台自动生成
- **发起人**：每流程必加，不可省略

### 3.2 发起人字段

| 属性 | 取值 |
|------|------|
| `prop` | `fqr` |
| 只读 | `disabled: true` |
| `resourceId` | 后端用户采集配置 ID（当前常量 `INITIATOR_RESOURCE_ID`；是否跨应用共用待两应用实测） |
| 采集字段 | 姓名 |

### 3.3 业务字段补充

- 样例 JSON 常不完整；**一键写入**时从 OA 原始表单提取结果补全
- 新增字段 **全部** 归入「表单信息」，排在部门/流程编号/发起人之后
- **不** 放入「审批意见」

## 4. 环节 key 与审批意见字段

**规律：** 环节 `taskKey` = 环节名称中文简拼；**同一职务在流程中出现第二次**时，环节名与 taskKey 末尾加 `2`（如汇聚后的「总裁办主任审批2」→ `zcbzrsp2`）。

| 环节名称 | taskKey | 审批意见 prop |
|----------|---------|---------------|
| 总裁办主任审批 | `zcbzrsp` | `zcbzrsp` |
| 总裁办主任审批2 | `zcbzrsp2` | （汇聚环节可无独立意见区） |

表单字段 **标题** 与 **prop** 与对应 USERTASK 的 taskName/taskKey 保持一致。

### 4.1 环节命名（需求加工层，非 VLM）

**原则：VLM 解析出什么文字，加工层环节名就用什么（+「审批」后缀），仅做下列明确变换，不做职务臆测替换。**

| 规则 | 说明 | 实现 |
|------|------|------|
| **忠实 parse** | 分支/串行 USERTASK 名来自对应 `WorkflowNodeItem.content` | `_task_name_from_content` |
| **不含具体人名** | 指南图常写「职务 + 姓名」；神笔只保留职务，人员由平台运行时维护 | `_strip_person_name` |
| **汇聚重名加 2** | 同一职务在流程中**第二次出现**（多路汇聚节点）→ 环节名与 taskKey 加 `2` | `_merge_task_name` → `zcbzrsp2` |
| **禁止** | 不得改职务用词（如副总经理→副经理、主任→副主任） | — |

**招聘·总裁办示例：**

- parse seq 5「总裁办主任」→ 分支环节 **总裁办主任审批**（`zcbzrsp`）
- parse seq 12「总裁办主任」（汇聚）→ **总裁办主任审批2**（`zcbzrsp2`）
- 两环节 parse 文字相同，靠「汇聚 + 加 2」区分；**不是**加工层改职务。

## 5. 表单操作权限（fromPropertyList）

| 角色 | 表单信息 | 审批意见 |
|------|----------|----------|
| **发起人**（STARTTASK） | 非只读业务字段 **writable**；部门/流程编号/发起人 **readable** | 全部 **readable**（不可写，**不得 hide**） |
| **当前审批人**（USERTASK） | 全部 **readable** | **本环节**字段 **writable**，其余审批意见 **readable**（不得 hide） |
| **抄送**（CCTASK） | readable | readable |

**实现要点：**

- `finalize_workflow_model` 须先补全 `properties`（复杂流程环节初始为 `null`），再写入 `fromPropertyList`
- 复杂流程 USERTASK 的 `taskKey` 与「审批意见」分组中对应 textarea 的 `prop` 一致，方可写本环节意见

代码入口：`core/workflow/shenbi_builder.py` → `_attach_form_permissions()` / `finalize_workflow_model()`

### 5.1 抄送节点拆分（指南 → 神笔）

指南流程图抄送框（含波形节点）常含 **多个抄送对象**，写入神笔时须拆成 **串行 CCTASK 链**，每个对象独立环节：

| 规则 | 说明 |
|------|------|
| **分隔符** | 中文顿号 `、`、中文逗号 `，`、英文逗号 `,`、分号 `;`、换行等 |
| **环节名** | `抄送{对象名}`；对象名去掉前缀「抄送」 |
| **示例** | 「野马集团招聘主管、野马集团招聘专员」→ `抄送野马集团招聘主管` → `抄送野马集团招聘专员` |

代码入口：`core/workflow/flow_semantics.py` → `split_cc_recipients()`；`complex_flow_builder.py` → `_build_cc_chain()`

## 6. 环节树（wfSimpleTaskInfo）

### 6.1 线性流程

- 结构：`STARTTASK → USERTASK → … → CCTASK`（`child` 串行链）
- `complexProcId = null`
- STARTTASK 必须有 `taskKey`（通常 `sqtb`）和 `taskName`

### 6.2 复杂流程

| type | taskKey/taskName | 分支 |
|------|------------------|------|
| STARTTASK | 有 | `child` 串行 |
| ROUTE | **无** | `conditions[]` 并行分支 |
| BRANCHTASK | 有 | `branchConditionList` 绑表单字段 |
| USERTASK / CCTASK | 有 | `child` 或挂在 conditions 下 |

**招聘需求样例中的判断字段：**

| 判断 | 绑定字段 | 含义 |
|------|----------|------|
| 8 路部门并行 | `zpbm`（招聘部门） | 发起人选部门决定分支 |
| 是否审计部 | `zpbm` | 选 **集团审计部(6)** → 野马集团总裁审批；选 **其余部门** → 职级分支 / 副主任链 |
| 是否经理及以上 | `zwjb`（职务级别） | 职级决定审批或抄送 |

### B. 环节类型（wfSimpleTaskInfo.type）

| 英文 type | 中文 | 说明 |
|-----------|------|------|

### D. 办事指南与解析

**分层原则（须遵守）：**

```
Word 流程图 → VLM 识别 → parse_result（忠实快照，不改写）
                              ↓
              guide_dag_compiler / flow_rules（需求加工）
                              ↓
              shenbi_builder → model-save JSON
```

| 层 | 职责 | 不改什么 |
|----|------|----------|
| VLM + parse_result | 与 Word 图文字、拓扑一致 | 不做神笔字段绑定、不做环节重命名规则 |
| guide_dag_compiler | DAG→环节树、zpbm/zwjb 绑定、taskName 规则 | 不回写 parse_result |
| shenbi_builder | 拼 formModel、审批意见列、registry | 不替代 VLM 识别 |

| 代码名 | 中文 | 说明 |
|--------|------|------|
| `parse_result` | 流程解析结果 | VLM 对办事指南流程图的**忠实** JSON，含节点列表 |
| `saved_at` / `source_mtime` | 缓存时间 / 源文档 mtime | Word 更新后 `source_mtime` 变化 → 缓存**过期**，须重新解析后再写入 |
| `WorkflowNodeItem` | 流程图节点 | 单节点：序号 seq、类型、文字、前后连线 |
| `prev_seq` | 前驱节点序号 | 汇入本节点的上游 |
| `next_seq` | 后继节点序号 | 本节点指向下游；长度 > 1 表示分叉 |
| `parallel_seq` | 并列节点序号 | 同一层级并行分支 |
| `DAG` | 有向无环图 | 办事指南流程图的数学结构（节点 + 有向边，无环） |
| `guide_flow_hints` | 流程匹配提示 | catalog 中用于在 parse_result 里定位对应流程图的标题关键词 |

**节点类型（node_type）中文：**

| 英文/原文 | 中文 |
|-----------|------|
| 开始节点 | 流程开始 |
| 结束节点 | 流程结束 |
| 处理节点 | 审批/处理 |
| 判断条件 | 菱形分叉 |
| 抄送节点 | 抄送 |

### E. 交付阶段（P0～P2c）

| 代号 | 中文目标 | 验收要点（简述） |
|------|----------|------------------|
| **P0** | 平台能写、能显、能跑 | 独立应用、菜单、办理人、写入校验、设计器非空 |
| **P1** | 与神笔样例对齐 | 开始环节名、表单 span、merge 保留环节树等 |
| **P2a** | 拓扑编译 | 指南 DAG → 环节树**结构**正确（分叉/汇聚数量对），分支条件可占位 |
| **P2b** | 分支绑定（招聘） | `zpbm` / `zwjb` 绑对，发起后选部门/职级走不同路径 |
| **P2c** | 通用化 | 多流程可生成；**Word 变更 → 重解析**；业务规则变更 → 改编译器/flow_rules |
